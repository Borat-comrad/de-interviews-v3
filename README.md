# Аналитика тарифов грузоперевозок

Конвейер `raw → core → mart` на PostgreSQL 17: очистка сделок, рыночный коридор
ставок и пакетный прогноз CatBoost. Исходные `sql/schema.sql` и
`sql/synthetic.sql` взяты из задания без изменений.

## Запуск

На машине с Docker и Compose:

```bash
docker-compose up
```

Современный эквивалент — `docker compose up`. Первый запуск создаёт 300 000
исходных сделок, заполняет хранилище, обучает модель и записывает прогнозы.
Готовность результата обозначается строкой `{"stage": "complete", ...}` в логе
`pipeline`; готовность контейнера PostgreSQL ещё не означает завершение расчётов.

По умолчанию цикл повторяется раз в сутки после завершения предыдущего прогона.
Частота и остальные параметры приведены в `.env.example`; при необходимости
скопируйте его в `.env`. Для однократной работы задайте `RUN_INTERVAL_SECONDS=0`.
Копирование `.env` для первого запуска не требуется.

Для локального прототипа БД использует `trust` внутри изолированной Docker-сети
без опубликованного порта. Пароли не зашиты в код. Если нужна парольная
аутентификация, до первого запуска задайте `POSTGRES_PASSWORD` и
`POSTGRES_HOST_AUTH_METHOD=scram-sha-256`; Python получает пароль через `PGPASSWORD`.

Повторный запуск и backfill (правая граница окна исключается):

```bash
docker compose run --rm pipeline python -m etl.pipeline --once
docker compose run --rm pipeline python -m etl.pipeline --once --start-date 2026-09-01 --end-date 2026-10-01
```

Дождитесь завершения стартового прогона перед ручным запуском. Одновременный
второй писатель отклоняется advisory lock. `--skip-ml` обновляет только Core и
рыночную витрину, оставляя прогнозы предыдущего полного прогона.

`N_PRICES` действует при создании нового тома источника. Повторная инициализация
не генерирует ещё одну копию данных. `docker compose down` сохраняет том с БД.

## Устройство

| Часть | Ответственность |
| --- | --- |
| `docker/` | Образ Python и атомарная инициализация источника |
| `sql/warehouse.sql` | DDL Core, карантина, рыночной и прогнозной витрин |
| `sql/load_core.sql` | Валидация, нормализация валют и категорий, загрузка связей |
| `sql/market_corridor.sql` | Квартили, доказательная база, календарные MoM/YoY |
| `sql/ml_dataset.sql` | Одна строка на сделку для ML |
| `etl/` | Подключение, транзакции загрузки, параметры окна и запуск этапов |
| `ml/features.py`, `ml/train.py` | Признаки, временное разделение, обучение и скоринг |
| `ml/repository.py` | Чтение обучающей выборки и пакетная запись прогнозов |
| `tests/` | Поведение DQ, витрин, повторных загрузок и защиты от утечек |

SQL обрабатывает данные наборами непосредственно в PostgreSQL; Python управляет
этапами. Прогнозы загружаются через `COPY`, без отдельных INSERT на каждую строку.
Это достаточная схема для данного объёма. Airflow, Superset и ClickHouse —
необязательные бонусы задания — не добавлены.

## Правила данных

- Окно ETL определяется по `loading_date`: `[start_date, end_date)`. Одна
  транзакция заменяет сделки, связи и карантин за окно. Удаляются также старые
  версии выбранных ID, если дата погрузки была изменена. Исправленные и удалённые
  записи учитываются при повторной обработке соответствующих окон.
- Карантин `core.dq_quarantine_prices` сохраняет исходную строку и все причины:
  невалидная цена/дистанция, отрицательный вес/объём, отсутствующий город,
  неизвестная валюта или отсутствующий/невалидный курс. `NaN` и бесконечности
  также не проходят. Для RUB цена должна быть строго больше 1000.
- RUB использует коэффициент 1; USD/EUR — точный курс по сохранённому
  `nearest_rate_date`. При отсутствии этой даты/курса — карантин. Поле не
  восстанавливается по `loading_date` или `created_at`: описание production-job
  в приложении трактуется как происхождение поля, а основной контракт задания
  требует точного соответствия сохранённой дате. При дублирующихся курсах берётся
  запись с минимальным `id`, чтобы JOIN не размножал сделки.
- В `core.cities` одна запись на `gc_id`, с минимальным исходным `id`. Регион —
  часть `full_name_local` после первой запятой; без неё — `Не указан`.
  Совпадающие города отправления и назначения сами по себе не являются ошибкой.
- Заполняются только отсутствующие весовые и объёмные категории. Вес перед
  классификацией округляется до 0,1 т; 30 т относится к `G20T`, 10 т — к `FTL`.
  Объём `0 < V <= 120` — `FTL`, остальные значения — `OTH`.
- Связи `price_body_types` имеют приоритет; если их нет, используется
  `prices.body_type`, затем `Не указан`. Дочерние типы объединяются по `std_id`.
  Ключ `(price_id, body_group)` не допускает повторной цены внутри одной группы.
- Факты для рынка: `is_fact`, `price_type IN (1,2,3,4,5,9)`, простой маршрут,
  положительная нормализованная цена и дистанция, `outlier_mark=false`.
  Цена считается уже указанной без НДС, как определено схемой задания.
- Месяц витрины берётся из `price_dates.price_date`; даты после `as_of`
  исключаются до агрегации. Несколько дат одной сделки внутри месяца схлопываются.
  Долгая заявка может входить в несколько месяцев и групп кузовов: такие счётчики
  нельзя просто суммировать между месяцами и кузовами.
- `carriers_count` считает организации только для типов 3 и 9. MoM и YoY
  сравнивают строго календарные месяцы; при пробеле возвращается NULL.
  Свежесть для HIGH — возраст максимальной допустимой `price_date` в ячейке,
  а не возраст первого дня месяца. Дополнительно нужны 30 сделок и 5 перевозчиков;
  MEDIUM — от 10 сделок, иначе LOW_DATA.

Рыночная витрина целиком пересчитывается после backfill: это обновляет также
соседние MoM/YoY и месяцы долгосрочных заявок. Перезапись атомарна, читатель
видит предыдущую версию до коммита. Core и Mart имеют отдельные транзакции:
при сбое этапа предыдущий успешный этап остаётся, повторный запуск безопасен.

## ML и результат

Дата снимка фиксирована: **2026-10-26**, независимо от даты запуска.

| Выборка | Окно по `loading_date` | Сделок |
| --- | --- | ---: |
| Train | `[2026-07-26, 2026-10-05)` | 24 226 |
| Test | `[2026-10-05, 2026-10-26]` | 12 808 |
| Future | после 2026-10-26 | 5 820 |

Train/test содержат только факты прямых перевозок без исходного флага выброса.
Будущие заявки с валидными данными и прямым маршрутом оцениваются независимо
от заполненного исходного тарифа и флага факта. Их фактическая цена и ошибки
в `mart.ml_price_predictions` всегда NULL.

Признаки заданы явным списком: отдельные города/регионы отправления и назначения,
координаты, расстояние, вес, объём, категории и кузов. Добавлены год, месяц,
день недели и день года, sin/cos для периодов 12, 7 и 365,25. Для сделки
с несколькими группами кузовов используется отсортированный набор групп
как одна категория: сделка не дублируется в обучении и метриках.

`price_rub`, производные тарифа, роли организаций, `outlier_mark` и
`price_group_stats` не входят в признаки. Масштабирования, таргет-энкодинга
вне CatBoost и дополнительного отсечения выбросов нет. CatBoost получает только
train; test не используется даже для early stopping. `has_time=True` сохраняет
хронологический порядок, seed=42. Обучение выполняется без открытой транзакции БД.

CatBoost выбран за обработку категорий и нелинейных зависимостей без отдельного
препроцессора. Используются 500 деревьев, depth=6, learning_rate=0,06, RMSE;
гиперпараметры не подбирались по test. Прогноз ограничен снизу одним рублём.

Результат на исходных 300 000 строках:

| Метрика на test | Значение |
| --- | ---: |
| R² | 0,920713 |
| MAPE | 15,4619% |
| RMSE | 53 867,84 руб. |
| MAE | 27 983,91 руб. |

Core содержит 299 797 сделок, карантин — 203, рыночная витрина — 203 644 ячейки.
В прогнозной витрине 18 628 строк. Параметры, признаки, границы и метрики
сохраняются в `mart.ml_model_runs`; идентификатор модели включает хеш обучающих
данных и параметров. Прогнозы данного `as_of` заменяются атомарно вместе
с метриками. Повтор не меняет численные результаты; время расчёта обновляется.

## Проверка

```bash
docker compose run --rm pipeline python -m pytest -q -p no:cacheprovider
docker compose exec postgres psql -U logistics -d logistics
```

Все 34 теста проходят. Они используют отдельную временную БД и удаляют её
после выполнения; проверяют также откат при ошибке записи и запрет
одновременных запусков.
В psql можно выполнить:

```sql
-- Карточка маршрута и квартильный коридор.
SELECT month, body_group, weight_category, p25_trip, median_trip, p75_trip,
       median_km, trips_count, carriers_count, mom_pct, yoy_pct, reliability_level
FROM mart.market_corridor
WHERE loading_city_gcid = 1001 AND unloading_city_gcid = 1003
ORDER BY month DESC, body_group, weight_category;

-- Причин может быть несколько на одну отклонённую строку.
SELECT reason, count(*) FROM core.dq_quarantine_prices, unnest(reasons) reason
GROUP BY reason ORDER BY count(*) DESC;

SELECT train_count, test_count, future_count, metrics FROM mart.ml_model_runs;
SELECT price_id, loading_date, actual_price_rub, predicted_price_rub, ape_pct
FROM mart.ml_price_predictions WHERE sample = 'test' ORDER BY ape_pct DESC LIMIT 10;
SELECT count(*) FROM mart.ml_price_predictions
WHERE sample = 'future' AND (actual_price_rub IS NOT NULL OR abs_error_rub IS NOT NULL OR ape_pct IS NOT NULL);
```

Последний запрос должен вернуть 0. Проверены повторный полный ETL и backfill
сентября: контрольные суммы всех строк Core, карантина и Mart совпали.
Независимый запуск с пустым томом воспроизвёл метрики и все 18 628 прогнозов.

## Ограничения источника

Последний день снимка, **2026-10-26**, ещё не прошёл ночную разметку аномалий:
`outlier_mark=false` не гарантирует отсутствия выброса. Флаг сохраняется как есть;
его пересчёт и подбор фильтров по test не выполняются.

Задание называет цель тарифом перевозчика, но требует историческую выборку
типов 1/2/3/4/5/9. Используется именно она: стоимость заказчика и экспедитора
не выдаётся за отдельный подтверждённый тариф перевозчика.

В источнике нет времени закрытия сделки и истории изменения справочников,
поэтому полноценное восстановление признаков «как было известно тогда»
невозможно. Используются `is_fact` и предоставленный снимок справочников.
Три месяца train также не покрывают полный годовой сезон; дальние будущие
прогнозы на этом снимке не имеют фактических меток для проверки.

После изменения справочников или курсов за старые периоды нужен соответствующий
backfill (полный прогон по умолчанию это покрывает). Отдельный CDC, хранение
бинарных моделей, высокодоступный кластер и бонусные BI-инструменты не реализованы.
